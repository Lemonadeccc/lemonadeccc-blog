# 文风画像

此画像来自三层来源：

1. `content/posts/zh/new-ai-tools-for-me.mdx` 当前版本相对 `HEAD` 版本的改写方向
2. 用户对 `content/posts/zh/cloudflare-r2-imgbed.mdx` 的手工回调修改
3. 用户对 `content/posts/zh/cloudflare-tunnel-de-vps.mdx` 的手工回调修改

## 核心转向

从“经验叙述 + 工具罗列”改为“问题先行 + 判断条件 + 最小流程”。

但这个方向需要控制强度。不是每篇文章都要改成“问题清单 + 边界 + 原则收口”的重写版。

## 主要变化

1. 开头从自我引入改成直接下判断。
原来先解释“这不是工具清单”，现在直接指出“单模型全流程生成”的适用边界，并马上列出具体问题。

2. 章节从名词分类改成动作分类。
原来是“设计阶段 / 开发阶段 / Skills / 测试流水线”，现在压成“明确需求 / 拆分执行 / 多模型协作 / 测试与评审 / 最小可复用流程”。

3. 表达从“我会怎么做”改成“什么时候应当这样做”。
原来强调个人流程，现在强调判断标准、适用前提和收口方式。

4. 内容从“覆盖更全”改成“保留论点所需的最小信息”。
原来列出大量 skills、配置和补充工具；现在只保留能支撑论证的工具和命令。

5. 论证从“收益描述”改成“收益 + 代价 + 边界”。
例如并行拆分不只写提效，也明确指出高耦合任务会提前暴露集成成本。

6. 结尾从“流程总结”改成“原则收口”。
最后不再只说“前期快、中期稳、后期可控”，而是收束为“AI 是需要约束、验证和收口的执行系统”。

## 句式特征

- 常用强判断句：`X 只适用于...`、`应先...再...`、`不应直接...`
- 常用对比句：`如果...，结果通常是...`
- 常用边界句：`这套方法也有边界。`
- 常用收口句：`此流程追求可控、可验、可维护。`

以上句式主要适用于总结、复盘、方法论文章。教程和部署文应更轻。

## 人工修订校准

`cloudflare-r2-imgbed.mdx` 和 `cloudflare-tunnel-de-vps.mdx` 的人工回调说明，当前 skill 需要同时支持“教程轻改”和“排障文保留事实列表”两种模式。

### 用户明确偏好的变化

1. 开头保留一句判断，但删掉了失效模式列表。
说明：短教程不必强行在开头加 3 到 5 个问题点。

2. 标题从“先确认适用范围 / 把 API 权限收紧到单桶”改成“适用范围 / API 权限”。
说明：标题应更短、更自然，少用命令式口吻。

3. 删掉了过度抽象的归纳句，例如“三件事配准”。
说明：不要为了显得结构化，硬造新的概念分组。

4. 保留必要判断，但弱化说教感。
说明：可以写“需要权限限制”，但不要每段都上升成原则宣讲。

5. 结尾改成轻量总结，而不是再强调一遍抽象方法论。
说明：教程文更适合用一句实用总结收尾，不一定需要“原则性收口”。

### `cloudflare-tunnel-de-vps.mdx` 进一步说明

1. 排障文可以保留开头列表。
说明：但列表应是“VNC 能进 / 端口监听 / UFW 未拦 / preauth reset”这类观测事实，而不是泛化风险点。

2. `summary` 可以更像压缩后的结论短句，而不一定写成完整劝告句。
说明：只要核心方法和问题场景都在，就不必强行加“应把”“先…”等措辞。

3. 检查说明应尽量单行化。
说明：像 `systemctl status ssh`、`ufw status` 这类命令说明，优先压成一条短说明，不需要再挂两层子 bullet。

4. 标题和链接文案可以继续收短。
说明：例如“买机中转”就比“香港机中转”更像实际操作时的口语表达，只要意思不丢即可。

5. 边界可以并回一句话，不必单独抬成“这套方法也有边界”。
说明：排障文更适合把取舍直接并入结论句，而不是再起一段解释。

## 强弱两档

### 重改

适用于：

- 方法论总结
- 复盘与排障
- 多工具流程整合

做法：

- 可加强问题先行
- 可补边界和代价
- 排障文可保留 3 到 5 个观测信号
- 可压缩出最小流程
- 可在结尾补一句原则性收口

### 轻改

适用于：

- 部署文
- 接入文
- 配置文
- 模板文

做法：

- 只改 `summary`、开头、标题和转场
- 操作步骤、表格、命令尽量原地保留
- 只补与当前步骤直接相关的一句说明
- 结尾优先写验收或一句轻量总结

## 结构模板

可优先套用以下顺序：

1. 一句判断，直接限制问题空间
2. 3 到 5 个具象问题或失效模式
3. 若干章节，每节遵循“判断 -> 方法 -> 边界”
4. 必要时保留可复用命令块或检查清单
5. 用最小流程总结，再用原则句收口

排障文可改为：

1. 一句问题场景
2. 3 到 5 个观测信号
3. 现状确认 -> 可选方案 -> 选定方案 -> 接入 / 验收
4. 结尾给出一条直接结论

## 编辑提示

- 遇到“常用工具 / 常用 skills / 常用配置”时，先判断是否真的支撑主论点
- 遇到长标题时，优先改成能表达动作的短标题
- 遇到泛泛总结时，改写成限制条件、验收标准或原则句
- 遇到长段经验描述时，优先抽成判断句和并列列表
- 如果原文本来已经是清晰教程，不要为了统一文风再额外加一段失败模式列表
- 如果改写后明显比原文更像“评论”而不是“教程”，说明改重了
- 如果是排障文，优先保留日志、状态、端口、返回值等证据，不要先做抽象升华
