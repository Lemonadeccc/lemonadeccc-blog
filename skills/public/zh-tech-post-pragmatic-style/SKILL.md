# ZH Tech Post Pragmatic Style

## 适用场景

在以下情况使用这个 skill：

- 目标文件位于 `content/posts/zh`
- 用户要“润色”“改写”“统一文风”而不是改主题
- 文章应从经验罗列改为更紧的判断式技术写法
- 但仍需保留原文类型，不把教程、想法、模板都改成同一种腔调

## 先判断文章类型

改写前先归类：

- 教程 / 部署文：以步骤、路径、命令、配置为主
- 总结 / 复盘 / 排障文：以判断、经验、取舍或故障定位为主
- 想法 / 规划文：以方向、约束、优先级为主
- 模板 / 示例文：以可复制结构或片段为主

改写强度：

- 教程 / 部署文：轻改为主，优先收紧表达、简化标题、补一两句适用范围
- 总结 / 复盘 / 排障文：可强化判断、边界和最小流程；排障文可保留观测信号列表
- 想法 / 规划文：强调约束、顺序和闭环
- 模板 / 示例文：通常只改 `summary`、开头说明和少量标题，不重写主体示例

## 改写流程

1. 先读全文，标出四类内容：
   - 自我叙述，如“我会”“我当前”
   - 工具堆砌或目录式罗列
   - 只有收益、没有边界的段落
   - 标题宽泛、无法表达动作和判断的章节
2. 先决定改写强度：
   - 如果是短教程或操作文，不强行新增问题清单、边界段和原则收口
   - 如果是总结、复盘或排障文，可以强化判断、观测信号、失败模式和最小流程
3. 重写开头：
   - 第一段直接给出适用范围、判断或限制条件，不做寒暄式引入
   - 只有在原文本来就偏排障、复盘、方法论时，才加入 3 到 5 个具体问题、观测信号或失效模式
   - 排障文的列表优先写“日志 / 状态 / 端口 / 现象”等事实，不先写抽象结论
4. 重写正文结构：
   - 标题优先短、自然、可索引，如“适用范围”“API 权限”“最小验收”
   - 只有在确实需要强调顺序时，再用“先…再…”式标题
   - 每节优先按“主题 -> 做法 -> 必要说明”展开，不强行每节都补边界段
   - 命令解释优先压成单行说明，避免一条命令后面再挂两层嵌套 bullet
5. 收缩信息密度：
   - 只保留支撑论点的工具、命令、流程
   - 相似工具不并列堆叠，除非它们承担不同角色
6. 重写结尾：
   - 总结 / 复盘文可压缩出“最小可复用流程”
   - 教程 / 部署文优先保留“最小验收”“注意事项”或一句轻量总结
   - 不要为统一风格强行补一个抽象口号式结尾

## 文风规则

- 少写“我怎么做”，多写“什么情况下应该这样做”
- 句子可以直接下判断，但不要每段都堆“应”“需”“才”“不要”
- 每段控制在 1 到 3 句，能拆成列表就不要堆长段
- 先压缩废话和重复，再决定是否补判断句
- 明确边界条件、失败条件和不适用场景，但只写和当前文章直接相关的
- 排障文的 bullet 优先写观测事实，不要先上升成空泛风险描述
- 保留必要术语和命令，但避免把文章写成工具清单
- 允许保留少量一人称，只在经验来源必须交代时使用
- 不要额外发明“三件事”“四层结构”这类新抽象，除非原文本来就有
- 教程文应保留操作密度，不要为了文风统一删掉关键路径、字段映射或命令
- 能用一句话写清的说明，不要拆成一串嵌套子 bullet

## 保留项

改写时保留以下内容，除非用户明确要求调整：

- frontmatter 字段与顺序
- MDX 语法有效性
- 代码块、命令、链接、图片路径
- 核心事实、产品名、文件名、命令名

## 禁止项

- 不要把“经验总结”写成宣传口径
- 不要为了完整性补充无关工具生态
- 不要把每节都写成“定义 + 列表 + 总结”的模板腔
- 不要只说优点，不交代适用边界
- 不要把结尾写成泛泛而谈的价值判断
- 不要机械加上“问题清单 + 边界 + 最小流程 + 原则收口”四件套
- 不要把教程文改成评论文，也不要把短文改得明显变长
- 不要把原标题都强行改成动作句；简洁名词标题通常更自然
- 不要把排障信号改写成抽象口号；日志、状态和现象应直接保留
- 不要把边界单独抬成一整段；能并入原句就并入原句

## 验收清单

完成后自检：

1. `summary` 是否从“内容清单”改成“方法或原则概括”
2. 开头是否直接提出适用范围、限制、问题或判断
3. 正文是否减少了自我叙述和工具堆砌
4. 是否只在必要处写出“不适用”“边界”“代价”，而不是到处硬补
5. 教程文是否保留了关键路径、字段映射、命令和验收动作
6. 排障文是否保留了关键症状、日志、状态和决策条件
7. 改写后是否更紧，而不是因为套模板明显变长
