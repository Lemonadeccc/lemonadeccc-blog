`RSI`（Recursive Self-Improvement）是系统通过修改自身改善能力，并继续参与后续改进的过程。涉及记忆、模型权重、工具、工作流和搜索策略，修改范围差别比较大。

早期的 `Gödel Machine` 提出先证明修改有益，再执行自修改。在实际系统中很难获得证明，工程上通常采用提出修改、运行任务、比较结果、是否保留去验证。

判断改进是否有效，还需要检查修改范围、任务迁移、回归情况和执行成本。

## 一、RSI 能力分层

按系统实际修改的内容，可以先分成四层：

| 层级 | 改什么 | 模型训练侧 | 应用开发侧 |
| --- | --- | --- | --- |
| L1 记住经验 | 外部记忆和经验文件 | 汇总错题、失败类型和数据问题 | 排障记录写入 `CLAUDE.md`、长期记忆、`Skill` |
| L2 利用反馈更新 | 固定优化流程中的权重或配置 | `STaR`、RLVR（如 `DeepSeek-R1`） | `DSPy` 优化 prompt，并保存为默认配置 |
| L3 修改工具及流程 | 执行代码、工具集、工作流 | 自动调整任务和课程组织 | `ADAS`、`DGM`、`DarwinX` |
| L4 改进优化方法 | 候选生成、筛选和搜索过程 | 改进训练或实验搜索策略 | `STOP`、包含改进器更新的闭环 |

分层用于区分修改范围，同一个系统可能同时涉及多层。

L1 能否跨会话保留，取决于存储和加载机制。经验写进文件并在后续任务中读取，就可以持续生效。

`Skill` 也不能固定归到某一层。补充一条经验和重写整套执行流程，实际改变的范围不同。

L4 需要检查改进器本身，在相同预算和新的任务上，是否更容易找到有效修改。任务分数上升，不能直接代替这项验证。

## 二、实验与案例

### DGM

Sakana AI 和 UBC 的 `Darwin Gödel Machine` 允许智能体修改自己的实现，并维护多个版本的存档。

基本流程如下：

1. 从存档中选择已有版本
2. 根据源码和任务反馈，生成工具、prompt 或工作流的修改
3. 在编程任务上分级评测
4. 保存有效版本，继续选择后续探索的分支

存档会保留部分暂时没有提升的版本，后续仍可继续修改。这样可以探索需要多次修改才能产生收益的路径。

此方法的改动包括补丁验证、多方案处理和上下文管理等。一次 SWE-bench 主实验约 80 次迭代，用时两周，API 成本约 2.2 万美元。

已有跨基准迁移收益，但还需要检查更大任务范围和不同预算下的稳定性。是否适合生产，还要结合复用次数、维护成本和新增推理开销判断。

### AlphaEvolve

DeepMind 的 `AlphaEvolve` 使用 Gemini 生成程序修改，再通过自动评测和进化搜索筛选。

报告结果包括：

- 通过使用 48 次标量乘法完成 4×4 复数矩阵乘法
- 改进 Google 数据中心调度策略，平均回收约 0.7% 的全球计算资源，相关方案已用于生产

此方法适合正确性和性能能够自动检查的问题。评测的可靠性、运行成本和吞吐，会直接影响可以尝试多少候选。

### STOP

`STOP`（Self-Taught Optimizer）修改的是用于改进程序的脚手架。

初始版本调用模型生成多个候选，再按效用函数选择结果。随后让这个改进器修改自身，搜索中出现了束搜索、遗传算法和模拟退火等策略。

此方法底层语言模型没有更新，因此没有将它称为完整的 RSI。其改进器代码已参与自修改，可以作为分析 L3、L4 边界的案例。

## 三、工程中的几类实现

### 1. 记忆更新：Reflexion、ExpeL

`Reflexion` 将任务反馈转成文字反思，保存后用于下一次尝试。反馈可以来自单测、环境状态，也可以来自模型生成的评价。

`ExpeL` 会比较多个任务中的成功和失败轨迹，提炼通用规则，并在新任务中检索相关经验。

两者都不更新模型权重。Reflexion 更侧重当前尝试的复盘，ExpeL 增加了跨任务经验提炼和检索。

实际使用时需要检查复盘依据。比如工具因鉴权失败而报错不能记录为增加重试。错误归因一旦进入长期记忆，会影响后续任务。

### 2. 参数更新：SPIN、SEED

`SPIN` 继续利用已有的人类回答进行训练：

1. 上一轮模型针对数据集中的问题生成回答
2. 使用人类回答和模型回答构造优化目标
3. 更新生成模型，再将新模型用于下一轮

论文的理论目标与模型分布贴近目标数据分布有关。这种方式可以继续利用已有数据，但没有额外引入独立的正确性来源。

`SEED` 将完成的轨迹整理成文字经验，再把经验带来的行为变化蒸馏到权重中。初始化阶段使用外部模型生成经验标注。进入 RL 阶段后，由当前策略同时承担执行和轨迹分析，并结合环境结果奖励训练。

此方法会更新权重，数据组织、训练目标和优化流程仍主要由人设定。

### 3. 结构搜索：ADAS

`ADAS` 使用 Meta Agent 生成 Agent 程序，调整推理组织、模块协作和反馈方式。

它参考存档中的设计和评测结果，提出新方案、编写代码、运行评测，再将结果加入存档。

搜索范围扩展到了代码，可以产生预设模板之外的组合，但仍受基础接口、运行环境和评测任务限制。

### 4. Harness 更新：DarwinX

`DarwinX` 冻结模型，只修改外部 harness，包括 prompt、工具、技能和控制流。

单独沿着当前最好版本持续修改，容易出现两类问题：

- 路径依赖：早期改动限制了后续探索范围
- 跨任务干扰：某类任务得到改善，另一类任务出现回归

对应做法是保留多个分支，并对晋升版本增加回归约束。

`preserve-and-extend` 要求修改带来净收益，同时将回归控制在允许范围内。候选还需要通过更严格的复测。总分较低的分支也会保留，用于后续组合互补能力。候选由各 benchmark 自身的 verifier 评测，仍然依赖明确的成功判定。

论文中循环内得分不能直接当作泛化效果。保留不同分支之后，仍需通过独立任务检查最终收益。

### 5. Skill 更新：SkillEvo

`SkillEvo` 通过多轮用户模拟，为技能修改持续提供反馈。

单轮 QA 只能暴露当前问答中的问题。修复之后，继续评测相似的一问一答，新增反馈可能很有限。多轮模拟会通过追问、补充条件等交互，暴露后续流程中的缺陷。

修改后增加独立治理检查，维护事实一致性和文件结构。除任务成功率外，再观察两项指标：

- 跨轮回归率：上轮通过、本轮失败的任务，占上轮通过任务的比例
- 内容膨胀：`SKILL.md` 和 reference 文件总行数，相对初始版本的增长比例

SkillEvo 和单轮 QA 使用开发集选择集合中最好版本。

### 6. 多智能体优化：MASS

`MASS`（Multi-Agent System Search）同时考虑 prompt 和拓扑结构。

多 Agent 存在级联依赖，前面模块的修改会影响后续输出。只依靠最终结果评分，中间模块又缺少直接反馈，联合搜索的组合空间会比较大。

MASS 分三步处理：

1. 优化构建块的 prompt，如聚合、反思、辩论、摘要和工具调用
2. 固定 prompt，探索拓扑结构，并根据贡献筛选模块
3. 在选中的工作流上联合调整 prompt，处理模块之间的依赖

实际应用中，prompt 优化比直接增加默认配置下的采样数量更有 token 效率。实际开发可以先调好已有构建块，再增加协作结构。

### 7. 联合优化：Self-HPO

只优化 harness 或模型权重，容易出现两侧不匹配。模型更新后，原先针对旧版本设计的流程可能不再合适。固定流程也会限制训练中能够获得的轨迹。

`Self-HPO` 交替执行两步：

- H-step：当前策略读取失败轨迹，修改 prompt 和运行逻辑，生成并评测 harness 候选
- P-step：在选中的 harness 下进行 RL，使用任务测试结果提供奖励

训练中仍未解决的任务，会进入下一轮搜索集，使 harness 修改继续针对当前策略的失败模式。

交叉组合实验中，优化后的 harness 配合原模型、优化后的模型配合原 harness，分别仍有收益。两者组合的增益超过单独增益之和。

其递归关系在于：提出下一轮 harness 修改的策略，本身也是上一轮训练的对象。外层 RL 算法、版本筛选规则和验证器仍由人设定。

## 四、瓶颈与进展

较容易取得收益的部分，通常都有比较明确的反馈。扩大任务范围后，主要需要处理以下问题：

1. **验证**：代码测试具备明确反馈信号也只能覆盖部分行为。写作、产品设计和研究方向选择，通常还需要人工判断或更长期的结果反馈。
2. **奖励**：执行器可能利用评测缺口。验证逻辑、评测数据和关键日志应有明确的修改权限边界。
3. **泛化回归**：固定题集上的提升，需要在留出任务、其他任务类型和不同模型上复测。已有迁移结果不能代替全部场景验证。
4. **成本收益**：搜索调用、评测环境、失败重试和最终版本的推理开销，都需要计入成本。研究阶段的分数提升不等于项目上的投入产出比。

按前面的分层，已有进展可以大致理解为：

- L1、L2 已有可用的记忆、配置优化和训练方法，能否取得稳定收益仍依赖具体任务和反馈质量
- L3 已在编程、算法和流程优化中得到实验结果，部分搜索结果已经用于生产
- L4 已有改进器自修改和联合优化原型，持续多轮、跨任务、预算可控的改进能力还需要更多验证

这里的层级不代表采用顺序。已有简单方案能稳定解决的问题，没有必要直接扩大到整套系统的自主修改。

## 五、判断改进有效

评估时可以固定检查四项：

1. **修改对象**：变化发生在记忆、权重、配置、工具代码，还是搜索方法
2. **验证依据**：使用单测、环境结果、人工 review 或模型评价，是否与实际目标一致
3. **迁移与回归**：未参与优化的任务是否改善，原先能完成的任务是否退步
4. **成本和改进效率**：同样预算下能找到多少有效修改，最终执行成本是否可接受

模型自评可以提供修改线索，但仅靠同一套自评结果选择版本，误判不容易暴露。重要改动应增加独立验证。

如需判断 L4，应将新旧改进器放在相同预算下，使用未参与优化的任务比较。一次搜索得到更高分，还不足以说明后续搜索能力已经提高。

应用开发可以将修改范围限制在 prompt、工具调用或失败恢复等能单独验证的环节。每次保留修改原因、版本和评测结果，确认收益后再扩大自动化范围。

后续仍需要持续补充失败样例、更新评测集和清理过期经验。自我改进循环能否长期运行，还要看这些修改在新任务中的效果，以及回归和维护成本能否控制。
