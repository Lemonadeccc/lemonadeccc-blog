This article is not a tool list, but a working method I distilled through repeated iteration in real projects.  
The process is to define the constraints clearly first, let multiple models execute in parallel, and then converge everything through a unified review.

## I. Design Stage

There are several possible routes in the design stage right now. Here I will only cover the stable ones.

### 1) Wireframe Sketches

- [wiretext](https://wiretext.app/): Quickly turns page structure into wireframes, which is useful for confirming the information hierarchy first.
- [mockdown](https://www.mockdown.design/): Uses text to express block-level page layout, which works well for early discussion and requirement clarification.

### 2) AI-Generated UI

- [Pencil](https://www.pencil.dev/): Generates editable UI drafts through prompts.
- [variant ai](https://www.variant.ai/): First find a style that is close, then adjust it with prompts; after exporting `.js`, continue refining the structure with Claude Code or Codex.

### 4) Common Skills
frontend-design(https://skills.sh/anthropics/skills/frontend-design): fairly general-purpose
ui-ux-pro-max(https://skills.sh/nextlevelbuilder/ui-ux-pro-max-skill/ui-ux-pro-max): multiple style sets, with automatic selection of the style that fits the scenario.
tailwind-design-system(https://skills.sh/wshobson/agents/tailwind-design-system): used when working with Tailwind
reponsive-design(https://github.com/wshobson/agents/tree/main/plugins/ui-design/skills/responsive-design): responsive design
[Copy UI styles from websites](https://github.com/Lucent-Snow/style-extractor): useful for copying styles.

## II. Development Stage

### 1) Baseline approach with Multiple Agents + Git Worktree

For simple requirements, my current way of splitting work is:

1. Break one requirement into 2-4 relatively independent subtasks.
2. Bind each subtask to its own worktree and its own session.
3. Merge small, verifiable increments first, then converge across modules.

This can significantly reduce context pollution and task interference.  
But it also has a boundary: when task coupling is too high, over-splitting worktrees amplifies integration cost.

### 2) Third-party tools

- [superset](https://github.com/superset-sh/superset): a parallel worktree orchestration tool.
- [happy](https://github.com/slopus/happy): remote control for cc.

Claude now officially covers multiple worktrees and part of the remote-control capability, so tools like these are better positioned as enhancement tools around other CLIs.

## III. CCG Workflow for Multi-Model Collaboration

`ccg-workflow` is responsible for process-oriented multi-model collaboration in this setup: Claude Code handles orchestration, frontend tasks are routed to Gemini first, backend tasks are routed to Codex first, and Claude performs the final unified review and lands the patch.

- Full workflow: `/ccg:workflow`
- Planning + execution split: `/ccg:plan` + `/ccg:execute`
- Task-oriented: `/ccg:frontend`, `/ccg:backend`, `/ccg:debug`, `/ccg:optimize`, `/ccg:review`

This approach can reduce the overhead caused by session switching and also reduce goal drift during implementation.

Built into ccg:
- Spec-driven (`/ccg:spec-*`):
  - Suitable for complex requirements with many constraints and a high chance of drifting off topic.
  - The value is turning "free-form generation" into "constraint-driven execution."
- Parallel implementation (`/ccg:team-*`):
  - Suitable for tasks that can be split into more than three independent modules.
  - The value is reducing context cross-talk through `/clear` + file-state handoff.

Configuration
- Adjust timeout parameters in `~/.claude/settings.json` (such as `CODEX_TIMEOUT` and `BASH_DEFAULT_TIMEOUT_MS`).
- Choose MCP tools based on complexity: ContextWeaver + Context7 / Playwright / DeepWiki / Exa.

## V. Testing and Review Pipeline

### 1) State the three-layer testing requirement clearly in the prompt

After implementation, I directly use this reusable instruction:

```text
请基于当前变更补齐并执行测试，要求：
1) 单元测试（unit tests）：覆盖核心函数、边界条件、异常路径。
2) 集成测试（integration tests）：覆盖模块间协作、数据流与接口契约。
3) 端到端测试（e2e tests）：覆盖关键用户路径（成功流 + 失败流）。

执行要求：
- 先写测试再修复实现，直到全部通过。
- 输出每类测试的新增用例清单、执行命令和结果摘要。
- 标注当前未覆盖风险点和建议补测项。
```

### 2) Cross-model code review

After the tests pass, I ask different models to do review separately, focusing on:

1. Potential bugs and edge-case issues.
2. Readability and maintainability.
3. Performance, complexity, and scalability risks.
4. Whether test coverage matches business risk.

The core benefit of multi-model review is reducing the blind spots of any single model.

### 3) Manual review

After AI review, I do one round of manual review, mainly to confirm:

1. Whether the requirement is actually closed-loop, rather than only satisfying the literal description.
2. Whether the changes introduce potential regressions.
3. Whether naming, boundaries, and error handling match team conventions.
4. Whether the tests cover the highest-risk paths.

The purpose of manual review is not to repeat AI conclusions, but to make business-context judgments and provide the final layer of risk control.

### 4) GitHub App automated review after CI

After a PR is submitted and CI passes, I add one more round of automated review with GitHub Apps. Common choices include:

- [Coderabbit](https://coderabbit.ai/)
- [Gemini Code Assist](https://codeassist.google/)
- [qodo](https://www.qodo.ai/)

I am also currently vibe-building a testing-focused [pr-agent](https://github.com/condevtools/pr-agent), which automatically summarizes "test results + risk points + review suggestions" into the PR or Issue to improve review and decision efficiency.

## VI. The current reusable end-to-end workflow

1. Use wireframe tools to clarify the information hierarchy and page structure.
2. Use UI generation tools to quickly get an editable first draft.
3. In development, prioritize the MVP first and push forward independent subtasks in parallel through worktrees.
4. For complex requirements, use `/ccg:plan` or `/ccg:spec-*` to lock down constraints before implementation.
5. Before merging, run a unified review (`/ccg:review` + manual spot checks), then do stabilization refactoring for robustness, maintainability, and boundary handling.

This workflow is fast in the early stage, stable in the middle stage, and keeps maintenance costs under control later on.
