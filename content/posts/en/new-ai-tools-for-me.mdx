I recently refactored my day-to-day AI workflow for real software projects.  
The objective is not tool maximalism. The objective is to reduce time-to-shippable-output at every stage.

## 1. Design Stage

The design stage has one rule: lock structure before spending cycles on visuals.

### 1) Wireframe Sketches: Align Information Hierarchy First

- [wiretext](https://wiretext.app/): Convert page intent into wireframes quickly, then validate information hierarchy.
- [mockdown](https://www.mockdown.design/): Express block-level layout in plain text for early requirement clarification.

### 2) UI Shell and Variants: Get an Editable First Draft Quickly

- [Pencil](https://www.pencil.dev/): Generate an editable UI draft from prompts.
- [variant ai](https://www.variant.ai/): Start from a nearby style, then iterate via prompts. After exporting `.js`, continue refinement with Claude Code or Codex.

At this point, "good enough to iterate" is the target quality bar.

## 2. Development Stage: Parallelization + Isolation Delivers the Biggest Gains

### 1) Multi-Agent + Git Worktree

My baseline execution pattern:

1. Split one requirement into 2-4 relatively independent subtasks.
2. Assign each subtask its own worktree and session.
3. Merge small, verifiable increments first, then converge cross-module changes.

This setup reduces context bleed and cross-task interference.  
Trade-off: over-splitting large features into too many worktrees can increase integration overhead.

### 2) Ecosystem Changes

I previously used:

- [superset](https://github.com/superset-sh/superset): parallel orchestration tool.
- [happy](https://github.com/slopus/happy): CLI wrapper.

Now that Claude covers multi-worktree workflows and part of remote execution natively, these tools are better treated as optional accelerators, not mandatory infrastructure.

## 3. CCG Workflow: Turning Multi-Model Collaboration into Process

`ccg-workflow` is the orchestration layer: Claude Code coordinates execution, frontend-heavy tasks are routed to Gemini, backend-heavy tasks to Codex, and Claude handles final review plus patch landing.

### 1) Installation and Prerequisites

```bash
npx ccg-workflow
```

- Requires `Node.js 20+`.
- Optionally install `Codex CLI` (backend-focused) and `Gemini CLI` (frontend-focused).

### 2) Common Commands

- Full workflow: `/ccg:workflow`
- Planning + execution split: `/ccg:plan` + `/ccg:execute`
- Task-oriented: `/ccg:frontend`, `/ccg:backend`, `/ccg:debug`, `/ccg:optimize`, `/ccg:review`

My preferred flow is plan-first execution:

```bash
/ccg:plan implement user authentication
/ccg:execute .claude/plan/user-auth.md
```

This lowers coordination cost across sessions and keeps implementation aligned with an explicit spec artifact.

### 3) Built-in CCG Capabilities

- Spec-driven (`/ccg:spec-*`):
  - Best for high-constraint requirements with scope-drift risk.
  - Value: convert free-form generation into constraint-driven execution.
- Parallel implementation (`/ccg:team-*`):
  - Best for work that naturally splits into 3+ independent modules.
  - Value: reduce context cross-talk via `/clear` plus file-state passing.

### 4) Configuration and Pitfalls

- Tune timeout parameters in `~/.claude/settings.json` (`CODEX_TIMEOUT`, `BASH_DEFAULT_TIMEOUT_MS`, etc.).
- Select MCP tools by problem complexity: ContextWeaver + Context7 / Playwright / DeepWiki / Exa.

## 5. MCP

Current Lighthouse MCP choice:

- `@danielsogl/lighthouse-mcp`: full-featured, supports Core Web Vitals, budgets, etc.

Two implementation notes matter in practice:

1. When running Lighthouse, explicitly ask the LLM to test both desktop and mobile. Many automated flows default to mobile only.
2. Automated Lighthouse scores can differ from manual DevTools runs. Use trend lines and bottleneck location as primary signals, not one-off absolute numbers.

If the site is on Cloudflare and audits hit crawler/access issues, first validate `robots.txt` and caching policy, then purge `robots.txt` cache and re-run.

## 6. Current Reusable End-to-End Workflow

1. Use wireframe tools first to clarify page structure and information hierarchy.
2. Use UI generation tools to quickly get the first editable draft and avoid over-investing in visual detail too early.
3. In development, prioritize MVP first, then parallelize independent subtasks with worktrees.
4. For complex requirements, use `/ccg:plan` or `/ccg:spec-*` to lock constraints before implementation.
5. Before merging, run unified review (`/ccg:review` + manual spot checks), then do stabilization refactoring (robustness, maintainability, edge handling).

Core principle: define constraints first, execute in parallel, and converge with a single review gate.  
This keeps early velocity high, mid-stage quality stable, and long-term maintenance predictable.
