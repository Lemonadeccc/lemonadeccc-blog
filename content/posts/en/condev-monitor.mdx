First, a quick introduction to the condev-monitor project. It is used to recreate a Sentry-like frontend monitoring system. It mainly includes the following parts: an SDK for monitoring errors and performance, an `examples/vanilla` frontend project for testing SDK integration, a `dsn-server` backend service that receives SDK error reports, and the dashboard frontend `frontend/monitor` with its backend `backend/monitor`.

At first, I planned to deploy with docker-compose on Coolify. After multiple attempts, the network kept being pruned internally by Coolify during deployment, and many other issues appeared. It might have been a conflict between Caddy in docker-compose and Caddy used by Coolify itself. After repeated failed attempts, I bought a new server and switched to a direct docker-compose deployment.

The project uses docker-compose and relies on many images. In development, it uses two database images, ClickHouse and Postgres, while other parts run locally with `pnpm start:dev` and `pnpm dev`. In development, `.env` files are maintained in each subproject. For production deployment, the two mainstream Next.js options are Nixpacks and Docker. For self-hosting needs, Next.js can use the OpenNext adapter for Cloudflare deployment, while the NestJS backend can run on an internal enterprise host through a tunnel. Another option is deploying both frontend and backend on an internal host via docker-compose. For the two backends, NestJS cannot be deployed without `node_modules`, so backend deployment either needs PM2 on the server or bundling `node_modules` into Docker images. I tried PM2 on the server, and also tried running OpenNext with PM2, but errors occurred. So I eventually chose full docker-compose deployment on the server. Up to this point, I had already gone through pitfalls with both Coolify and the PM2 + docker-compose hybrid approach.

I used Alibaba Cloud with a 2C2G AliLinux server for Docker image deployment and kept hitting OOM crashes. I also had no budget for swap. So I later planned to run backend services with PM2 and containerize only ClickHouse and Postgres, but the deployment process was too cumbersome and I dropped it, then moved to full docker-compose deployment. In the dashboard NestJS backend, using `argon2` failed to compile on Alibaba Cloud due to the default Python 3.6. I tried switching to Python 3.7 and recompiling, but it still failed. Since this kept happening, I replaced the encryption dependency with `bcryptjs`.

Another issue during docker-compose deployment on Alibaba Cloud: when using the older `nest-modules/mailer` package in the dashboard NestJS backend, it reported missing CSS-in-JS dependencies. There were solutions in GitHub issues, but they were not standard and the steps were tedious. Future maintenance would likely be harder, so I switched to `nodemailer`.

OOM kept happening on Alibaba Cloud servers, so I moved to an external Netcup 4C6G machine. This avoided complicated ICP filing and Docker image setup, and also avoided future OpenAI regional availability issues in China when developing other AI projects. The full image deployment with docker-compose completed normally, but tests showed that email sending/receiving did not work. After testing server scripts, I found SMTP sending was not supported on that machine. So based on the previous `nodemailer + 163 SMTP` setup, I now prioritize Resend's HTTP email service, and fall back to SMTP when HTTP sending fails. This ensures email service remains available when critical errors occur.

So far, these are the errors and pitfalls encountered in dependency replacement and deployment for this project.
